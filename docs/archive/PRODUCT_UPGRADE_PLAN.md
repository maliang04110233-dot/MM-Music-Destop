# MusicDL 完整产品化升级方案

生成时间：2026-06-13
项目位置：`C:\Users\59443\WorkBuddy\2026-06-06-19-21-10\music-downloader`
目标：从“多平台音乐下载工具”升级为“可长期使用的桌面音乐管理与下载产品”。
优先约束：功能尽快丰富，同时保持基本稳定。

---

## 1. 当前系统现状

当前 MusicDL 已经不只是一个简单下载脚本，而是一个 Electron 桌面应用。它已经具备以下基础能力：多平台搜索、网易云 / QQ / B 站下载链接解析、下载队列、ID3 写入、歌词获取、本地音乐库扫描、播放器、Cookie 登录、首页推荐、用户偏好持久化、部分单测与基础模块拆分。

目前主进程已经拆成了 `src/main/ipc/*` 子模块，API 层已经拆成了 `src/api/platforms/*`，CSS 已从 `index.html` 中拆出，说明项目已经具备继续产品化迭代的结构基础。

但当前仍存在一些明显短板：renderer 业务 JS 仍集中在 `index.html` 的 `<script>` 中；首页推荐仍依赖第三方非官方 SDK，接口不稳定；没有统一日志系统；没有下载历史；没有完整的失败诊断；没有用户可视化设置页来管理所有偏好；本地库还没有索引数据库；没有断点续传；打包、升级、崩溃恢复、自动更新都还没产品化。

---

## 2. 产品化目标

建议把 MusicDL 升级成三个核心模块组成的桌面产品：

第一是“发现音乐”：聚合网易云、QQ、B 站首页、榜单、歌单、搜索、推荐流；第二是“下载管理”：支持单曲、批量、歌单、失败重试、任务历史、音质策略、歌词/封面/ID3；第三是“本地音乐库”：支持自动扫描、播放、筛选、标签编辑、封面歌词补全、去重、播放列表。

用户体验目标是：打开应用即可看到首页推荐；搜索或点歌单即可批量加入下载；下载任务可恢复；本地音乐无需每次选择目录；播放器有基本队列和歌词；出错能明确告诉用户是 Cookie、VIP、接口失效、网络还是版权限制。

---

## 3. 升级路线总览

建议分四期推进。

P0 是“稳定化与基础设施”，目标是让现有功能不再频繁因为重构而破。包括补全日志系统、错误码、设置页、任务历史、状态持久化和基础测试。

P1 是“功能快速丰富”，目标是补齐最容易感知的产品功能。包括 QQ 首页完整复刻、网易云首页、B 站音乐首页、歌单批量下载、专辑下载、下载历史、本地库自动恢复。

P2 是“体验升级”，目标是让应用像一个正式播放器和下载器。包括播放器队列、收藏、播放列表、歌词同步体验、封面墙、下载详情页、失败诊断面板。

P3 是“长期产品化”，目标是支持长期迭代。包括 SQLite 本地数据库、插件化平台适配、自动更新、崩溃日志、打包签名、可配置代理、下载限速、任务导入导出。

---

## 4. P0：稳定化与基础设施

### 4.1 统一日志系统

现在错误分散在 `console.warn`、`console.error`、Toast 和 renderer console 里。建议新增 `src/utils/logger.js`，在主进程写入 `userData/logs/app-YYYY-MM-DD.log`。日志分为 info、warn、error、debug 四级。renderer 通过 IPC 上报关键错误。

这能解决当前反复出现的“启动报错但要人工复制控制台”的问题。未来用户只要点“导出诊断日志”，就能定位错误。

### 4.2 统一错误码

建议新增 `src/shared/errors.js`，定义错误码：`VIP_REQUIRED`、`AUTH_EXPIRED`、`LOGIN_REQUIRED`、`NETWORK_TIMEOUT`、`PLATFORM_CHANGED`、`COPYRIGHT_RESTRICTED`、`NO_AUDIO_STREAM`、`UNKNOWN_PLATFORM` 等。

API 层返回统一结构：

```js
{ ok: false, code: 'VIP_REQUIRED', message: '该歌曲需要会员 Cookie', platform: 'qq', retryable: false }
```

下载队列、Toast、日志都基于错误码展示不同 UI。

### 4.3 设置中心升级

当前设置主要是 Cookie 管理。建议扩展为正式设置中心，包括下载目录、本地库目录、默认音质、并发数、是否下载歌词、是否写 ID3、是否自动扫描本地库、代理设置、日志级别、缓存清理、Cookie 管理。

偏好已经有 `prefs.json` 基础，可以继续扩展。

### 4.4 下载历史

当前只有下载队列 `queue.json`，已完成任务可以清除，但没有长期历史。建议新增 `history.json` 或 SQLite 表，保存下载成功/失败记录、文件路径、平台、音质、错误码、时间。

下载历史能支持：重新下载、打开文件、查看失败原因、统计下载量。

### 4.5 renderer JS 拆分

`src/renderer/index.html` 仍包含大量业务 JS。建议拆成：`js/app.js`、`js/state.js`、`js/views/home.js`、`js/views/search.js`、`js/views/local.js`、`js/views/settings.js`、`js/player.js`、`js/toast.js`、`js/utils.js`。

这不是纯洁癖问题，而是降低后续功能开发的回归风险。

## 5. P1：功能快速丰富

### 5.1 QQ 音乐首页完整复刻

建议把 QQ 首页拆成这些区块：焦点图、猜你喜欢、推荐歌单、官方歌单、分类歌单、排行榜、新歌首发、热门歌手、热门电台、每日推荐。当前已开始接入 `recommend/playlist/u`、`recommend/playlist`、`top`、`new`、`radio`、`singer` 等接口。

下一步要做的是把 QQ 首页单独做成一个 `QQHome` 视图，而不是简单塞进当前“首页推荐”列表里。UI 上应支持 QQ 内部 tabs：推荐、歌单、榜单、新歌、歌手、电台。

### 5.2 网易云首页升级

网易云侧建议接入：飙升榜、热歌榜、新歌榜、原创榜、推荐歌单、精品歌单、每日推荐、新碟上架、歌手榜。若 Cookie 可用，则展示私人推荐；无 Cookie 则显示公共推荐。

### 5.3 B 站音乐首页升级

B 站侧建议接入：音乐区排行榜、VOCALOID、翻唱、演奏、MV、热门 UP 主、收藏夹导入、视频音频提取。B 站内容不是纯音乐，需要更明确标注“视频音频”。

### 5.4 歌单批量下载

这是最有价值的功能之一。用户打开歌单后，可以一键“全部加入队列”，支持跳过已下载、跳过失败、只下载未下载、按音质批量下载。

需要新增：批量任务分组、批量进度、批量失败摘要。

### 5.5 专辑下载

网易云和 QQ 都支持专辑维度。建议增加“专辑详情页”和“下载整张专辑”。专辑目录命名建议为：`艺术家/专辑名/曲序 - 标题.ext`。

### 5.6 下载命名模板

用户可配置文件命名：`{artist} - {title}`、`{album}/{track} - {title}`、`{platform}/{artist}/{title}`。这对长期整理本地库非常重要。

## 6. P2：体验升级

### 6.1 播放器升级

当前播放器能播放、切歌、循环、随机。建议增加播放队列面板、当前播放列表、收藏、最近播放、播放历史、迷你模式、播放进度记忆。

### 6.2 歌词体验升级

当前歌词能读 LRC 并同步滚动。建议增加歌词字体大小、歌词偏移调整、双语歌词、桌面歌词、歌词重新匹配、手动导入 LRC。

### 6.3 本地音乐库升级

建议本地库引入持久索引，避免每次全盘扫描。短期可用 `library.json`，长期建议 SQLite。功能包括自动扫描、增量扫描、去重、标签缺失提醒、封面缺失提醒、歌词缺失提醒、按歌手/专辑/年份/格式筛选。

### 6.4 任务中心

当前下载队列只显示近期任务。建议升级为任务中心：等待中、下载中、失败、已完成、历史记录。失败任务要能批量重试、按错误码筛选。

### 6.5 首页加载策略

首页不应一次性等待所有平台接口返回。建议改成“骨架屏 + 分区懒加载”：QQ 区块先显示，网易云区块再显示，B 站区块独立显示。每个区块失败只显示该区块错误，不影响整个首页。

---

## 7. P3：长期产品化

### 7.1 SQLite 数据库

当功能扩展到下载历史、本地库索引、播放历史、收藏、任务组时，JSON 文件会越来越难维护。建议引入 SQLite。Electron 里可用 `better-sqlite3`，但它是原生模块，打包需要处理。也可以先用纯 JS 的 `sql.js`，但性能较弱。

建议表：tracks、downloads、playlists、play_history、settings、platform_accounts、lyrics_cache、cover_cache。

### 7.2 自动更新

如果要分发给别人用，需要 electron-updater。版本升级时要有迁移脚本，例如 prefs.json 到 SQLite 的迁移。

### 7.3 平台适配插件化

现在平台逻辑是 `platforms/netease.js`、`qq.js`、`bilibili.js`。长期建议定义统一 PlatformAdapter：search、getUrl、getLyrics、getPlaylist、getAlbum、getHome、verifyCookie。

这样未来加酷狗、酷我、咪咕，不会污染聚合层。

### 7.4 代理与网络诊断

音乐平台接口经常受地区、Cookie、限速影响。建议支持 HTTP 代理、超时配置、DNS 失败提示、接口健康检查。

### 7.5 崩溃恢复

应用异常关闭时，应恢复下载队列、播放器状态、上次页面、本地库目录，并给用户提示“上次异常关闭，是否恢复任务”。

## 8. 推荐实施顺序

第一轮建议做 P0：统一日志、错误码、设置中心、下载历史、renderer JS 拆分。预计 1-2 天。

第二轮做 P1 的“首页平台内容升级”：QQ 首页单独成页、网易云首页、B 站首页，采用分区懒加载。预计 1-2 天。

第三轮做“批量下载闭环”：歌单详情页、全选、加入队列、任务组、失败重试。预计 1 天。

第四轮做“本地库产品化”：持久索引、增量扫描、去重、缺失元数据提示。预计 2 天。

第五轮再做 SQLite、自动更新、插件化等长期工程。

---

## 9. MVP 建议

如果想最快看到产品感，建议先做这个 MVP：

首页改为三平台 tabs，每个平台独立加载自己的完整首页。QQ 页面包括推荐、歌单、榜单、新歌、歌手、电台；网易云页面包括榜单、推荐歌单、每日推荐；B 站页面包括音乐区排行和分类。每个区块有“一键加入队列”。下载队列支持任务组。设置页支持默认音质、下载目录、本地库目录。

这个 MVP 做完后，用户打开应用就能浏览、点歌单、批量下载、看进度、失败重试，产品感会明显提升。

---

## 10. 主要风险

第一，平台 API 不稳定。QQ/网易云都是第三方或逆向接口，必须允许局部失败。第二，Cookie 风险。Cookie 明文存储目前可用，但长期建议用 safeStorage。第三，下载合规风险。应始终保留学习研究声明，不鼓励分发内容。第四，重构风险。之前已经多次遇到闭包、IPC、时序 bug，后续每次拆模块都必须先写测试或加临时日志验证。

---

## 11. 结论

可以升级，而且值得升级。当前项目最适合的路线不是马上引入复杂数据库或大重构，而是先把“用户能明显感知”的功能补起来：完整首页、歌单批量下载、下载历史、本地库自动恢复、设置中心。与此同时，补日志和错误码作为安全网。

建议下一步先做 MVP：平台首页完整化 + 分区懒加载 + 歌单批量加入队列。
